## CLI and built-in interactive commands

`apps/tui/src/cli-main.ts` currently accepts `--mode text|json`, `--provider`,
`--model`, `--thinking`, `-e|--extension`, `-c|--continue`, `-r|--resume`,
`--session`, `--session-dir`, `--diagnostics`, `--verbose`, `-h|--help`,
`-v|--version`, `--` and positional prompt text. Subcommands are `update`,
`savings` and `acp [login]`. `--session-dir` requires `--session`; `--resume` and
external extensions are interactive-only; headless needs a prompt. Preserve
these validations. **No `daemon` subcommand exists yet**; S1.14 adds management.
The isolated `--daemon-runtime` selector is also planned, not an existing flag.

### Optional provider registration: llama.cpp

`piExtensions.llamaCpp` defaults to false. When enabled for an interactive root,
`pi-extensions.ts` calls `pi-llama.ts::resolvePiLlamaCppExtensionPath` to load the
bundled Pi adapter. Its `extensions/llama/index.js` registers the `llama.cpp`
provider and `/llama`, whose UI lists, downloads, loads and unloads router models.
`provider.js` contains server URL/auth/catalog behavior; `huggingface.js` has
token lookup with ambient HOME/env defaults. This is not a 25th Felan extension
package and must not silently disappear in the extraction.

S1.05 owns registration/model/auth binding. LLAMA_BASE_URL and Hugging Face
lookup retain normal daemon-launch env/HOME behavior under the superseding user choice. S1.09 owns the subsequent command/UI
split, S1.12 its presenter. Registration remains session-scoped; one session's
provider/catalog registrations must not overwrite another's; the launch environment is shared intentionally. Preserve the
interactive-root allowlist boundary—do not enable this optional adapter in
ACP/headless or permit arbitrary providers solely because they registered.
The static probe reads these installed files; it does not start llama.cpp or
make Hugging Face requests.

## UI categories and known unsupported surfaces

- `select/confirm/input/editor` become bounded broker schemas; no client means
  pending, not approval. Host trust/install/MCP callback prompts require local TUI.
- `notify/setStatus/setWidget` text/`setTitle` become data. Working indicators,
  hidden-thinking labels and tool activity use snapshot state. Escape untrusted
  terminal controls, retain intentional renderer styling.
- `custom`, component widgets, footer/header/editor components, terminal-input
  hooks, editor insertion, themes, shortcuts, autocomplete and renderCall/Result
  execute only in the client. The generic daemon bridge must return an explicit
  `unsupported` result when no matching presenter exists, never hang or approve.
- Existing `ext-ask-user/tui` is a useful precedent, but most default exports
  currently mix execution and Pi TUI imports. Merely setting `ctx.mode` is not an
  import boundary. S1.09's tests must prove daemon entrypoints do not import
  presenter code and client entrypoints do not import environment implementation.
- Arbitrary external extension `ui.custom` closures/components cannot cross a
  process boundary. A compatible, versioned presenter is required. Third-party
  shortcuts/editor hooks/header/footer/theme internals without such an entrypoint
  are explicitly unsupported. Generic structured tool rendering still works;
  prompt/approval primitives must remain brokered. This is a disclosed limitation,
  not an excuse to lose any built-in row above.
- Arbitrary trusted in-process extensions can also bypass `AgentRuntime`, read
  sibling state or mutate globals. Shared launch-environment behavior is not a
  sandbox/security guarantee; loading such code remains a trust decision. The
  original per-session `getEnv` contract was superseded by the user; no new
  environment accessor is required.
- ACP continues its current advertised initialize/load/close/prompt/cancel and
  optional form elicitation/terminal-login surfaces. It does not acquire TUI
  panels, model/mode selection, images, additional directories or MCP injection.
  `session/close` and EOF detach; TUI may answer pending ACP approvals.
  Only registered daemon sessions are resumable. Pre-daemon files require an
  explicit import into a new ID and are never adopted or modified.

S1.09 and S1.12 must turn every row/category into an implemented-or-explicitly-
unsupported test entry. S1.15 fails on an unexplained built-in loss. Current
in-process tests establish prior behavior, not daemon acceptance.
